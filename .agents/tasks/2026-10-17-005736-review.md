The branch `feat/m1-skeleton` builds out the full M1 skeleton: a Tauri v2 React/TS shell, a FastAPI engine sidecar with loopback + bearer auth, a Rust supervisor that mints a per-session token and a free loopback port, spawns the engine, health-checks `/healthz`, and restarts with capped exponential backoff, a single typed TS client the UI talks through, i18next (id default + en), and a three-job Windows CI workflow. **Verdict**: APPROVED

## High-level view

The supervisor is a genuinely thin process manager with no business logic: it generates a 256-bit OsRng token, reserves a free loopback port by binding `127.0.0.1:0` and releasing it, spawns the engine (dev `python -m texora_engine`, prod the `texora-engine` externalBin), polls `/healthz` via a blocking `ureq` call, and restarts on failure with a capped geometric backoff. The token is passed through the `TEXORA_ENGINE_TOKEN` env rather than argv to avoid process-listing leakage, and a failed status emit never crashes the loop.

The Rust/TS contract is coherent: `EngineState`/`EngineStatus` serialize camelCase and match the TS union + interface exactly; the command name `engine_status` and event `engine://status` agree on both sides. The single-client invariant holds — `engineClient.ts` is the only production module importing `@tauri-apps/api`; the three other importers are test files that mock the bridge. All UI strings route through i18next with `id` as default and `en` as fallback.

The engine keeps `/healthz` open and guards `/engine/info` with a constant-time bearer check sourced from `app.state`. The capability scopes `shell:allow-execute` to the `binaries/texora-engine` sidecar with argv validators for host/port/token; dev-mode Python spawning goes through Rust core (not the WebView), so the narrow scope does not block it.

The CI workflow is valid YAML with three `windows-latest` jobs, `build-installer` gated on both check jobs, pinned action and tool versions, and every referenced script/path present. `docs/LICENSES.md` has a row per manifest dependency, the `reqwest` candidate is resolved to `ureq` with no leftover row, and PyMuPDF/Surya are correctly listed as opt-in only.

The honesty posture is correct: the frozen 14.9 MB sidecar is gitignored (only `.gitkeep` tracked), and the three host-limited items are flagged as pending, never reported as green.

### Supervisor: token, port, spawn, backoff

`supervisor.rs` is the core of task 1.4 and stays within the "thin secure process manager, no business logic" rule. `generate_token()` draws 32 bytes from `rand::rngs::OsRng` and hex-encodes to 64 lowercase chars; `free_loopback_port()` binds `127.0.0.1:0`, reads the OS-assigned port, and drops the listener. The TOCTOU window between releasing the port and the engine binding it is acknowledged in a comment and is acceptable for a single-user loopback app.

The spawn path passes the token via the `TEXORA_ENGINE_TOKEN` env in addition to argv, specifically to keep it out of process listings on platforms that expose argv — a deliberate hardening choice worth noting. Dev mode runs `python -m texora_engine` (interpreter resolved via `TEXORA_ENGINE_PYTHON`, then the engine venv, then `PATH`); prod resolves the `texora-engine` sidecar through `tauri-plugin-shell`, so externalBin `-$TARGET_TRIPLE` resolution is Tauri's responsibility.

The health loop polls `/healthz` up to 80 times at 250ms, then, once healthy, re-probes every 5s and surfaces a silent hang as `Unhealthy`. `publish` swallows emit errors so a failed broadcast never kills the loop, and a never-healthy child is explicitly killed before the backoff restart. The backoff is pure and unit-tested (geometric, capped, resets after a healthy run). Seven Rust unit tests cover port reuse/reachability, token length/charset/uniqueness across 1000 draws, backoff increase/cap/reset, and camelCase serialization — none spawn a real engine.

### Rust/TS status contract and the single-client invariant

`EngineState` and `EngineStatus` derive `serde(rename_all = "camelCase")` and skip `None` fields; the TS `EngineState` union and `EngineStatus` interface in `engineClient.ts` mirror this exactly, and `engine_status` / `engine://status` names agree on both sides. `engineClient.ts` is the sole production importer of `@tauri-apps/api` (grep across `apps/desktop/src` confirms the only other importers are `App.test.tsx`, `engineClient.test.ts`, `EngineStatusBadge.test.tsx`, all mocking it). The badge consumes the client and renders i18next strings only, with `role="status"`, `aria-live="polite"`, and an aria-label composed from translated text.

### Engine auth and capability scope

`routes.py` keeps `/healthz` open (200, no auth) and mounts `/engine/info` on a router carrying the `require_token` dependency. `security.py` reads the expected token from `app.state.engine_token` and compares with `secrets.compare_digest`, rejecting absent/non-bearer/mismatched credentials with 401. The capability grants `core:default` plus `shell:allow-execute` scoped to `binaries/texora-engine` with argv validators (`\d+` for port, `[0-9a-f]+` for token). Because dev-mode Python spawning runs through Rust core rather than a WebView `Command`, the sidecar-only scope does not block dev spawning — a subtlety the integration notes call out correctly.

### CI workflow

`ci.yml` parses as valid YAML (re-confirmed with PyYAML): `engine-checks` and `frontend-checks` both on `windows-latest`, `build-installer` on `windows-latest` with `needs: [engine-checks, frontend-checks]`. Actions and tools are pinned (checkout@v5, setup-python@v6/3.11.9, setup-node@v5/24.x, pnpm/action-setup@v4/9.15.9, upload-artifact@v5, dtolnay/rust-toolchain@stable, Swatinem/rust-cache@v2). The freeze step passes `--python python` because `engine/.venv` does not exist on a runner, and `--triple x86_64-pc-windows-msvc` to skip the rustc probe. The end-to-end "artifact installs and launches" criterion is honestly flagged as runnable only on a real runner + manual install.

### Licenses and honesty posture

`docs/LICENSES.md` carries a row for every dependency in `engine/requirements*.txt`, `apps/desktop/package.json`, and `Cargo.toml`, including dev tooling; versions match the manifests. The `reqwest` candidate is resolved to `ureq` (sole `/healthz` client) with no leftover row, and PyMuPDF (AGPL) + Surya (GPL code / non-commercial RAIL weights) are documented as opt-in only, never default — matching the permissive-first steering.
